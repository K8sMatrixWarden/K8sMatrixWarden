What this is

K8sMatrixWarden is a Kubernetes security scanner. Its whole surface, scanning, the CIS benchmark, the threat matrix, kill-chain attack paths, and scan×runtime correlation, is reachable from the CLI and the web dashboard, both running the same engine and saving to the same report store. It is detect-and-report only, read-only on every surface, no apply/remediate path.

Every check is a Rule, a technique-level detection that self-declares which MITRE tactic, OWASP category, CIS control, and NSA/CISA guidance it maps to. That means the exact same engine answers "scan the production namespace", "scan for Privilege Escalation", and "scan only Container Escape", the request just changes which rules get selected, never the code path that runs them.

Install and first scan

The core engine has zero required dependencies, it runs on the Python standard library alone, against a bundled, deliberately-insecure mock cluster.

Requirements

Python 3.10, 3.14, and nothing else. Because the core imports only the standard library, no third-party package can lag a new Python release. The 3.10 floor comes from the optional extras, kubernetes and pyyaml each require 3.10+, not from the engine, which uses no version-gated syntax and none of the stdlib modules removed in 3.12, 3.13.

How It Works

One idea drives the whole design: shards and tactics are orthogonal.

How It Works

The core agents

Three agents, one shared registry, one execution path for every kind of request, resource-scoped, tactic-scoped, or plain English, all read-only.

AgentPurposeRuns as
OrchestratorClassifies intent, extracts scope, resolves the selector against the registry, manages confirmationsSingle entry point
ScannerRegistry-driven scanning across 7 domain shards; resolves any scan to a rule setDeployment (HPA)
RuntimeReal-time syscall + K8s audit-event matching against the same tagged-rule pattern; correlates live events to static findings + detects driftDaemonSet, 1/node
◈

The Orchestrator never scans directly, it compiles every request, from either entry point (CLI flags or a natural-language query), into one internal ScanRequest object and delegates. That's what makes "scan a namespace" and "scan for Persistence" the same code path.

How It Works

Two orthogonal axes

The Scanner is built on one deliberate separation everything else depends on:

  • Domain = the execution boundary. Rules are grouped by the evidence pattern they share, pods, the RBAC graph, image layers, network objects, cloud IAM. This is where code, the evidence fetch, and scoped RBAC live.
  • MITRE tactic / framework = cross-cutting tags. A rule carries tags owned by no single shard. A hostPath mount legitimately serves Persistence and Privilege Escalation and Lateral Movement, it lives in one shard but is reachable from three different tactic queries.

How It Works

One pipeline, not several

Each engine being right in isolation does not make the tool coherent. The failure mode that matters is an engine producing correct, richer structure that the next stage quietly drops.

Kubernetes Evidence
   -> Static Findings + RBAC Graph + NetworkPolicy Graph + Runtime Events
   -> Reachability
   -> Evidence-Backed Attack Graph
   -> Confidence  ->  Risk  ->  Threat Matrix  ->  Historical Posture
   -> CLI / Web / Reports

Every transition preserves resource identity (cluster, namespace, kind, name), evidence provenance (which object, and why), and confidence. The integration is asserted rather than assumed: tests/test_integration_pipeline.py runs real scans over purpose-built clusters and follows one fact from evidence to every user-facing surface.

ScenarioWhat it proves
Internet → Ingress → Service → Pod → SA → RoleBinding → Role → secrets/getThe whole chain is one evidence-backed path, and the binding that grants it is named in the report and the dashboard.
NetworkPolicy blocks the pathReachability context changes; severity, exploitability and blast radius do not.
Policy uses matchExpressionsIsolation is recognised exactly as with matchLabels, so a protected pod is not reported as internet-reachable.
Policy cannot be evaluatedpartial, and the pod stays reported as reachable. An unconfirmed restriction is never treated as protection.
Runtime evidence on the podThe finding reaches full confidence and the path becomes observed, at the hop the event named, with the rest still configuration-derived.
Runtime event in another namespaceNothing changes. Activity elsewhere is not evidence about this finding.
Runtime contradicts declared postureDrift is detected, and the originating event travels with the finding.
Partial / unreadable evidenceCoverage drops with an honest basis, findings are unaffected, and the unread kind is named in the report.
Same workload in two namespacesFindings, reachability, RBAC, attack paths and the timeline stay separate throughout.
Malformed cluster objectThat one workload loses its reachability context; the scan, the paths and the reports all still complete.

Cross-surface consistency

Given one scan, the CLI, the JSON and SARIF reports, the HTML document, the web API and the dashboard present the same findings, the same identities, the same risk and the same attack paths. They differ in formatting, never in security meaning, because none of them recomputes anything: the core is authoritative and each surface renders what it is given. The single formula deliberately implemented twice (a finding's display anchor, in Python and in the dashboard's JavaScript) is covered by a drift test.

The Scanning Engine

The Scanning Engine

The rule model

The atomic unit of detection self-declares its own taxonomy, authored once, indexed centrally at startup, so "scan for Persistence" is an O(1) lookup, never a full-registry scan.

rule anatomy
Rule(
  "workload-privileged-container", "Privileged container",
  owning_shard="workload_pod_security",
  resource_scope=["Pod"], severity=CRITICAL,
  detection_method=STATIC_CONFIG, check=_priv,
  mitre=[MitreTag(PRIVILEGE_ESCALATION, "T1610", "Deploy Container"),
         MitreTag(EXECUTION,            "T1610", "Deploy Container")],
  owasp="K01", cis=["5.2.2"], nsa_cisa=["Pod Security"],
)

At startup, every shard registers its rules and the MITRE Mapping Engine indexes every tag into six lookup tables: tactic, technique, OWASP, CIS, NSA/CISA, and module. A selector resolves against these indexes directly, never a scan across all 55 rules.

✓

Anti-drift by construction. Tags live with the rule's logic, not in a separate mapping file that can go stale. The test suite fails if any rule references a MITRE technique id absent from the vendored ATT&CK-for-Containers taxonomy, or if a composite alias targets a rule id that doesn't exist.

The Scanning Engine

The risk score, exactly

Four multiplications. One normalization. No hidden weights.

core/scoring.py
issue_score    = severity_weight × exploitability × blast_radius × path_multiplier × reachability_multiplier
reachability_multiplier = 1 + 0.5 × [Internet-reachable] + 0.25 × [ServiceAccount can reach secrets]
path_multiplier = 1 + 0.25 × (distinct_tactics_on_finding − 1)   # attack-path bonus

raw            = Σ issue_score over WORKLOAD ISSUES    # one per (rule × owning workload)
cluster_risk   = 10 × raw / (raw + K)                  # K = 60.0, saturating
security_score = round((1 − cluster_risk / 10) × 100)  # 0, 100

Two counts: evidence, and things to fix

Kubernetes represents one workload as a chain of objects, so a Deployment whose pod template runs as root produces that finding on the Deployment, on every ReplicaSet it has created, and on every Pod. Three findings, one misconfiguration, one edit to fix it. A live scan of an eight-namespace cluster produced 517 findings of which 353 sat on such derived objects. Every report therefore publishes two numbers, under names that cannot be read as each other:

CountMeaning
resource_findingsEvery Kubernetes object carrying a flaw. The evidence, unchanged and never hidden, the findings table, the JSON and the API all still list each one.
workload_issuesOne per (rule × owning workload). The number of separate fixes. This is what the risk score is summed over.

Scoring on issues stops a controller's chain multiplying the score. It is not a discount and nothing is divided: two workloads with the same flaw still score twice, two rules on one workload still score twice, and a standalone Pod scores on its own. Grouping follows Kubernetes ownerReferences only, never a name prefix or a similarity, so Deployment/api and Deployment/api-server stay two workloads, and namespace and cluster are part of workload identity, so the same name in two namespaces or two clusters never collapses. A Pod whose controller is absent from the evidence keeps its own identity rather than being attached to a plausible-looking parent.

Runtime evidence is a separate concept and is not aggregated this way: five shell executions in one workload remain five runtime alerts.

FactorValues
severity_weightCRITICAL 10 · HIGH 7 · MEDIUM 4 · LOW 1 · INFO 0
exploitabilityRemote 3 · Adjacent 2 · Local 1
blast_radiusCluster-wide 3 · Namespace 2 · Pod 1
path_multiplier1.0 (1 tactic) · 1.25 (2 tactics) · 1.5 (3+). Attack-path bonus for multi-tactic findings.
cluster_riskRating
0.0, 2.0🟢 Excellent
2.1, 4.0🟢 Good
4.1, 6.0🟡 Fair
6.1, 8.0🟠 Poor
8.1, 10.0🔴 Critical
n/a⚠️ Unknown, the scan could not read the cluster, so no rating is possible. Explicitly not a passing grade.

Reachability tagging: a separate axis that never moves the score

After scoring, core/reachability.py tags every workload finding with how an attacker reaches it, but it never lowers severity, exploitability, or blast_radius. A real misconfiguration is a real thing to fix regardless of reachability; the tags decide triage order, not whether. Each finding's exploitable_by carries one or more of:

TagMeaningFix lever
🔴 ingressA NodePort/LoadBalancer Service or Ingress fronts the pod and no NetworkPolicy isolates it, reachable from outside the cluster today.Remediate + cut exposure (NetworkPolicy / drop external Service)
🟡 pod-privilegeNot externally reachable, exploitable only after an attacker already has code execution in a pod (assume-breach).Remediate for defense-in-depth (lower urgency)
⚠ rbac-escalationThe pod's ServiceAccount holds a cluster-admin escalation lever (wildcard, bind/escalate, impersonate, create-pods, or read-secrets).Scope the ServiceAccount's RBAC

On a live kubernetes-goat + DVKA scan this turns 368 flat findings into a triage queue: 74 fix-now (internet-reachable or escalate-to-cluster-admin) vs 270 post-breach-only, with nothing hidden and no severity changed. For deep multi-hop attack-path graphs, optional passthrough runners in integrations/external_graph.py invoke KubeHound and IceKube.

The Overview surfaces this as a pod-exposure inventory bar: reachability.inventory() classifies every in-scope pod (not just flagged ones) into one worst-wins bucket, internet + cluster-admin > internet-reachable > cluster-admin SA > post-breach-only, so the segments sum to the real pod total. The denominator is the point: "380 pods, 4 internet-reachable" reads very differently from "4 of 4", and a clean cluster shows an almost-entirely-quiet bar.

Where a finding stops being theoretical.

Runtime and Correlation

The runtime agent

The same rule/registry pattern as the Scanner, applied to a live event stream instead of cluster state, Falco-style syscalls and Kubernetes audit events, each tagged with its own MITRE tactic.

DetectsSourceTactic
Shell spawned in a containerfalcoExecution
Metadata API access (169.254.169.254)falcoCredential Access
Network recon tool (nmap, masscan, nc)falcoDiscovery
Crypto-miner signaturefalcoImpact
Container escape indicator (release_agent, nsenter)falcoPrivilege Escalation
Container log cleared/truncatedfalcoDefense Evasion
New (Cluster)RoleBinding createdauditPrivilege Escalation
Exec into kube-systemauditExecution
Secret enumeration via APIauditCredential Access
K8s events deletedauditDefense Evasion
Mass-deletion spike (≥10)auditImpact

Every runtime detection is tagged surface=runtime, the explicit split from the Scanner's point-in-time surface=scan rules. Alerts come back carrying surface + source. In production, events arrive from Falco (via falcosidekick) or the Kubernetes audit log posted to /api/runtime; installing Falco is left to the operator.

Scan × Runtime correlation: the differentiator

Scanning alone is table stakes (Trivy, kubescape, and kube-bench all do it). The differentiator here is correlation + causality: not "here's a weakness" but "this weakness is being exploited right now, and here's the kill-chain." A static finding says "this config is weak" (point-in-time); a runtime alert says "this behaviour just happened" (live stream). Joined on the MITRE tactic they already share, they answer the question a responder actually has.

SignalWhat it means
confirmedRuntime alert matches a static finding on the same resource and the same tactic, the weakness is being acted on. When several weaknesses on that resource share the tactic, the event does not say which was the vector, and the dashboard lists every candidate.
corroboratedSame tactic, behaviour aligns with a known static gap.
runtime-onlyLive behaviour with no matching static finding, something the scan never predicted (often the most interesting).
driftRuntime behaviour that contradicts a Pod's declared posture (uid 0 despite runAsNonRoot, a write despite readOnlyRootFilesystem, a privileged-only op from a non-privileged pod), the strongest signal, because a control the operator thinks is enforced is not.detect_drift

Both are pure functions of (findings, events), no cluster access, no re-scan. Events that can't be attributed to a scanned pod are skipped, not guessed, keeping false positives near zero. From the hit cells of the threat matrix, build_attack_path chains a full kill-chain (Initial Access → … → Impact) with entry points and a reaches-Impact flag.

Five confidences

Five different confidences now exist, because they answer five different questions. They are kept apart on purpose: collapsing them into one number is how a scanner ends up sounding certain about evidence it never read.

ConfidenceAnswersValues
EvidenceWas this resource type read, and how do we know the fraction?measured · estimated · heuristic · unknown
AssessmentHow much of the cluster did the scan see?0, 100%, a function of coverage only, never of severity
FindingHow much to trust this conclusion?0, 1, with the reasons that produced it
CorrelationHow tightly does a runtime event tie to a static finding?confirmed · corroborated · runtime-only
Attack pathHow strongly is this route evidenced?configuration-only · corroborated · observed

The five rules that keep them coherent

  1. Nothing is more confident than the evidence under it. If a resource type could not be read, no claim is made about it, and the absence is reported rather than a confident silence.
  2. Only a resource-level runtime match earns certainty. Activity elsewhere in the namespace corroborates and is capped below it.
  3. A runtime event at one hop does not make a multi-hop path observed. The path records which hops were witnessed (observed_nodes) and states plainly that the remainder is configuration-derived (fully_observed: false).
  4. Confidence never changes severity and never hides a finding. A low-confidence CRITICAL is still a CRITICAL to triage, it just needs verifying first.
  5. unknown and partial are values, not synonyms for false or safe. They propagate as themselves through coverage, NetworkPolicy, RBAC, the reports and the dashboard.
ℹ

The policy lives as CONFIDENCE_POLICY in core/explain.py, next to the code that applies it, and every rule above is asserted in tests/test_integration_pipeline.py, so the documentation and the behaviour cannot drift apart.

Attack paths, two layers

Two findings sharing a tactic are not connected by anything except the label. Pretending otherwise is how a scanner starts inventing attack chains.

LayerWhat it claims
Tactic (steps)Tactics with findings, in kill-chain order, the ATT&CK-navigator convention. Adjacency, deliberately not causality.

ConfidenceMeaning

corroboratedRuntime activity matches the path's namespace, but no event named its own resource.

Bounded analysis

Graph traversal has to stop somewhere. The danger is not the bound, it is a bounded result that looks exhaustive.

Every bounded analysis therefore reports its own status:

analysis_status: complete
analysis_status: truncated   truncation_reason: edge_limit | onward_target_limit

BoundValueWhy it exists
RBAC edge budget8Admits a two-identity chain (bind, grants, enables ×2 plus one reaches hop). A third identity is not more true, only longer, and multiplies the path count.

Traversal is cycle-safe: a visited set means a mutual-impersonation loop (legal RBAC, and it happens) terminates and returns the shortest path rather than spinning. Results are deterministic, ordered by hop count, then capability directness, then rendering, so the same evidence always produces the same paths in the same order.

Graph and Evidence Analysis

RBAC as a graph

Not "does this ServiceAccount hold a dangerous verb", but "here is the binding, the role and the hop sequence by which it reaches cluster-admin".

Principal (ServiceAccount / User / Group)
    --bound-by-->   RoleBinding | ClusterRoleBinding
    --grants-->     Role | ClusterRole
    --permits-->    verb on resource
    --enables-->    escalation capability
    --reaches-->    another Principal / an admin ClusterRole   (the second hop)

Two rules keep the claims honest, because an attack path that is not true is worse than no path at all:

  • Every edge is evidence-backed. An edge exists because a specific collected object says so, and it carries that object's identity and the reason.
  • A second hop needs its target to exist. "Can bind any ClusterRole" becomes an escalation only if an admin-equivalent ClusterRole was actually collected; otherwise the capability is reported with no onward hop.

Traversal is breadth-first with a visited set and an edge budget, so a cyclic RBAC graph (A can impersonate B, B can impersonate A, which is legal and does happen) terminates and returns the shortest path. Namespaces are respected: a namespaced permission never reaches another namespace's identities.

Capabilities modelled: cluster-admin, bind-roles, impersonate, create-workload, exec-pods, read-secrets, modify-bindings. Reachable on each finding's rbac_paths, and spliced into the reachability chain shown in reports and the dashboard.

NetworkPolicy semantics

Matching only matchLabels under-matches real policies: a policy selecting pods by expression looks like it selects nothing, so an isolated pod reads as exposed. And egress was invisible entirely.

SupportedDetail
matchLabelsAll keys must match.
matchExpressionsIn, NotIn, Exists, DoesNotExist. A pod without the key satisfies NotIn, as Kubernetes specifies.
podSelectorOn the policy and on peers. An empty selector selects everything in the namespace.
namespaceSelectorResolved against collected Namespace objects, including the built-in kubernetes.io/metadata.name label.
ipBlockcidr plus except. 0.0.0.0/0 and ::/0 are allow-all.
policyTypesKubernetes defaulting: omitted means Ingress, plus Egress only when egress rules exist.
Ingress and egressBoth directions evaluated. Policies are additive, so one allow-all rule defeats a strict sibling.

Each direction returns a status:

StatusMeaning
unrestrictedNo policy governs this direction, the Kubernetes default.
allow-allGoverned, but a rule admits every peer. Not isolation.
restrictedGoverned, every rule names specific peers, which are returned.
deny-allGoverned with no rules at all.
partialA selector this build cannot evaluate. The restriction is not confirmed and is never treated as isolation.
unknownNo NetworkPolicy evidence was collected.

Egress feeds context rather than a tag: unrestricted egress means a compromised process can reach any in-cluster service and the internet (an exfiltration / C2 path), which is stated in the finding's explanation without altering its severity.

Evidence coverage

A risk score says how bad what we saw is. It says nothing about how much we managed to see. Those are different questions, and conflating them is how a scan of a cluster whose Secrets and Nodes were unreadable gets read as a clean bill of health.

Every scan therefore carries three numbers, not one:

NumberAnswers
Risk scoreHow bad the findings are (core/scoring.py)
Evidence coverageWhat fraction of the requested evidence the scan actually read
Assessment confidenceHow much weight to put on the risk score, given that coverage

Coverage is structural, not a guess: the Evidence Collector records the outcome of every resource type it was asked for, and core/coverage.py aggregates it per kind and per domain (Workloads, RBAC, Network, Secrets, Node configuration, Control plane, Admission control, Cloud IAM). Each number also carries how it was arrived at, so an estimate never renders like a measurement:

BasisMeaning
measuredCounted exactly. A clean read is 100%, a skipped type is 0%, both known rather than inferred.
estimatedA truncated read where the API reported remainingItemCount, so the fraction is computed from real numbers.
heuristicA partial read with no basis to compute a fraction. The fallback value is flagged, never presented as counted.
unknownTruncated with no remaining count available. The fraction is not known and no number is invented.
⚠

Low coverage never suppresses, downgrades or hides a finding: what was seen was seen. And a scan that could not read the cluster at all is rated Unknown with confidence None, never "Excellent".

Graph and Evidence Analysis

Posture over time

k8smatrixwarden posture answers "did we get better or worse, and because of what?", new, resolved, persistent, regressed, plus MTTD and MTTR.

Two honesty rules decide what may be called a fix:

  • A finding is resolved only when the current scan actually ran the rule that found it. A narrower re-scan silently "resolving" everything it did not run is the classic false-green, so those land in not_rescanned instead.
  • A regression is a finding that was seen, fixed, and is back. That needs history, so it is derived from the store's timeline rather than from two scans.

Scope identity

The timeline accumulates across scans and resolves whatever a scan did not re-observe. That is only sound within one security context: a namespace-scoped scan of staging must not mark a cluster-wide finding in production as fixed, and a scan of cluster B must not resolve cluster A's history. Every entry is therefore keyed by:

<cluster>@<scope>#<rule_id>|<kind>|<name>|<namespace>

c1@cluster-wide#workload-privileged-container|Pod|payment-api|production

Both halves come from the existing model (ScanResult.cluster_name and Scope.describe()), no new concept was introduced. The resolve sweep only ever touches entries sharing the current scan's scope, and posture compares against the previous scan of the same scope, not merely the same cluster.

Timeline records written before scoping existed have no prefix. They stay readable, remain visible to a scoped read (so an upgraded store keeps detecting regressions against the history it already had), and are never resolved by a scoped scan.

Detect and report only

K8sMatrixWarden never mutates the cluster. Every surface, the CLI and the web dashboard, is read-only: scanning uses get/list/watch only, and every output (reports, threat matrix, attack path, dashboard) is derived from that single read-only snapshot. Performance characteristics

  • Evidence is fetched once per scan, cached by kind, shared across every resolved rule. This is the efficiency property the whole architecture exists to guarantee, a tactic scan touching Pods and webhooks fetches each list exactly once, no matter how many rules read them.
  • Rules execute in a thread pool (parallel_rules, default 16). In live mode this overlaps API-bound and CPU-bound rules; each rule is individually guarded, so one throwing an exception becomes an INFO engine-error finding rather than a failed scan.
  • Selector resolution is O(1) index lookups built once at startup, never a scan over rule code.

GET /runtime-management, /runtime-events, /runtime, /runtime/eventsAll resolve to the Runtime tab of the single-page dashboard: the event feed as a filterable table with an expandable per-event detail view, distinguishing K8sMatrixWarden curated detections, relayed Falco detections, Kubernetes audit events and configuration drift.
GET /healthLiveness + rule/shard counts.
◈

The dashboard binds 127.0.0.1 by default and is read-mostly, the only state-changing routes are POST /api/scan (a read-only scan that saves its result) and POST /api/runtime (ingests events and returns correlation + drift; it never touches the cluster). The tool detects and reports only, there is no remediation/apply path on any surface. Saved-report lookups are path-traversal-guarded, and --no-scan serves existing reports fully read-only.

Troubleshooting

ModuleNotFoundError when running python -m k8smatrixwarden

Run it from the repository root (the folder containing the k8smatrixwarden/ package), or install it once with pip install -e . and use the k8smatrixwarden command from anywhere.

Emoji or box-drawing characters render as ? on Windows

The CLI already forces UTF-8 on its own streams. If output is still garbled, run chcp 65001 in the terminal first, or use -o text for a plain-ASCII report.

"Selector matched no rules"

Typo in selector. Run rules or coverage to see valid values, or scan --dry-run to check.

--live fails with import error

pip install -e ".[live]".

"Cannot reach the Kubernetes API server"

Cluster stopped or wrong endpoint. Tool preflights with kubectl cluster-info; web returns 400 {error}, never 500.

"Kubernetes API authentication failed"

Credential plugin failed (cloud profile misconfigured). Fix with aws configure, gcloud auth login, az login. Fatal at preflight to avoid 0-findings-Excellent scoring.

0 findings + rating Unknown

Every resource forbidden (blanket 403). Check RBAC. Use roles --bind for minimal ServiceAccount. Partial coverage also gets amber "Partial coverage" banner.

Some 403 errors during live scan

Inaccessible resource types skipped + recorded as warnings. Scan completes with everything else. Re-rendered report shows partial-coverage banner.

CIS report shows many NEEDS_NODE controls

Expected, need on-node file reads. Run kube-bench, pass --kube-bench-json. On managed cluster: --profile eks|gke|aks.

Is the tool over-privileged?

k8smatrixwarden roles prints minimal ClusterRole (get/list/watch only per shard). roles --bind shows full manifest before apply.

Known limitations

Stated plainly, because a security tool that overstates its coverage is worse than one with less of it.

LimitationWhat it means in practice
Synthetic evidence buckets in live modeComponentConfig (control-plane flags) and CloudIAM (workload-identity bindings) have no direct Kubernetes API. Control-plane flags are largely recovered from kube-system static-pod specs; the remainder needs kube-bench JSON, and cloud IAM needs a cloud adapter. The rule logic is already written and fires the moment those buckets are populated.
Trivy / kubescape adapters are seams, not wired binariesExternalToolAdapter defines the interface and the fold-in point; the subprocess calls are stubs. The CIS engine is not a stub, it is fully built, 130 controls, with kube-bench wired for the 31 file-permission controls.
The Runtime Agent is a catalog + matcher, not a live tailIt evaluates an event stream, real or simulated, and Falco ingestion is built and tested (POST /api/runtime). Running Falco in-cluster so events stream continuously is deployment work, not code work.
The dashboard has no authenticationIt binds 127.0.0.1 deliberately. On any non-loopback bind a request-supplied kubeconfig is refused with 403, because loading one executes its credential plugin, see Safety Controls.
Falco's probe needs a real kernelIts eBPF probe attaches tracepoints on the node's own kernel. Nested virtualization (e.g. minikube's docker driver inside Docker Desktop's Linux VM on macOS) blocks that attachment: the pod starts and rules load with no error, but zero syscalls are ever captured. Not a configuration problem, a kernel-access one; a real node (cloud cluster, bare metal, Docker Desktop's VM directly) has no such limit. The dashboard's Runtime tab has a Try with sample events button that demonstrates confirmed / corroborated / runtime-only correlation from the current scan's own findings, pushed through the real /api/runtime path, with no Falco required (core/runtime_demo.py).
Natural-language parsing is deterministic, not an LLMCurated synonym patterns plus fuzzy "did you mean" over terms generated from the registry, so phrasing can never drift from what actually exists.
Correlation joins on tactic + namespace, not resource nameA same-namespace tactic match is called confirmed; tactic-only is corroborated. Tightening confirmed to require the same resource waits on reliable k8s.pod.name enrichment from Falco.
The seccomp rule inspects only the first containerA documented simplification in shards/workload_pod_security.py.

Remaining threat-matrix gaps

Scan coverage is 77.8%, or 85.2% counting Runtime Agent detections, which are reported as their own state and never folded into scan coverage. The remaining gaps are genuine: CVE scanning (waiting on the Trivy adapter), backdoor-container provenance, cloud service-principal mounts, and three techniques that would require adding a Lateral Movement tactic to existing Credential Access rules. That last one is deliberately not done, extra tactics inflate the attack-path multiplier and would silently move every historical score.

Roadmap

K8sMatrixWarden ships today as a complete detect-and-report platform. The following enhancements are planned, each building on infrastructure that is already in place.

  • Native live collectors. Direct in-cluster collectors for ComponentConfig and CloudIAM evidence, complementing today's kube-bench JSON ingestion and cloud IAM inputs, the rule logic is already written and runs identically in mock and live mode.
  • First-class Trivy / kubescape adapters. Wiring the external-tool adapter seams into live subprocess calls, on top of the fully built native CIS engine.
  • In-cluster Falco feed. The correlation and drift layer, Falco-event ingestion (POST /api/runtime, normalize_events) are built and tested; the next step is verifying it end to end on a node with real kernel access, where Falco's probe can attach.
  • Per-finding causal attack graph. Extending the kill-chain attack path from tactic-ordered chaining into a per-finding causal graph (e.g. pod-A's ServiceAccount reaching binding-B), surfaced across every report format.
